# Авторизация и переход с ручного токена

Новая установка выбирает «Вход через Яндекс». Существующие настройки с токеном
или Client ID распознаются как ручные: обновление не меняет подключение, baseline,
очереди, пароль, device ID или допуск к автоматической синхронизации. Выбор способа
в интерфейсе — локальный draft. Только сохранение ручного токена или успешное
сохранение нового OAuth grant меняет действующее подключение.

## Включение общего приложения владельцем

В `src/auth/configuration.ts` настроен публичный Client ID, предоставленный
владельцем приложения. Включён вход через код в браузере; `callbackPlatforms`
пока пуст. Права приложения, Redirect URI и реальный PKCE-обмен ещё требуют
проверки у провайдера и на устройствах. При пустом Client ID интерфейс объясняет
недоступность общего входа и предлагает ручной способ. Нельзя использовать
идентификатор чужого приложения.

1. Зарегистрировать собственное приложение Яндекс ID **для авторизации
   пользователей**, с правами `cloud_api:disk.read` и `cloud_api:disk.write`.
   Не выбирать приложение только для собственных данных разработчика.
2. Проверить обмен `authorization_code` с PKCE S256 без Client Secret, включая
   повторное согласие и второй аккаунт. Настроить разрешённые redirect URI;
   кодовый путь использует `https://oauth.yandex.ru/verification_code`.
3. Проверить `obsidian://yandex-disk-sync-auth?vault=<URL-encoded vault name>`
   на каждой платформе, обработку query parameters и ограничения регистрации
   redirect URI у провайдера. Только проверенные платформы добавить в
   `callbackPlatforms`. Пока список пуст, применяется кодовый путь.
4. Внести только публичный Client ID в конфигурацию. Client Secret не включать
   в плагин. Пройти `TC-AUTH-01` и обычный smoke двумя профилями на реальном Диске.

Refresh не реализован: возможность обновления токена публичным клиентом без
секрета не подтверждена. Ответный refresh token не сохраняется. Метаданные имеют
поле для него и различают grant, но эта схема не означает поддержку refresh.
При истечении или отзыве доступа требуется новый явный вход. Сохранённый срок
действия — метаданные, API остаётся источником фактической доступности токена.

Источники протокола: [запрос кода и PKCE](https://www.yandex.ru/dev/id/doc/ru/codes/code-url),
[кодовый путь](https://yandex.ru/dev/id/doc/ru/codes/screen-code),
[регистрация](https://yandex.ru/dev/id/doc/ru/register-client),
[тип приложения](https://yandex.ru/dev/id/doc/ru/register-auth),
[refresh](https://yandex.ru/dev/id/doc/ru/tokens/refresh-client).
Права, Redirect URI и работоспособность конкретного приложения ещё не подтверждены
ручной приёмкой.

## Пользовательский поток

На первой настройке пользователь выбирает отдельную удалённую папку, проверяет
фильтры и нажимает «Войти и синхронизировать». Плагин открывает внешний браузер.
После согласия callback возвращает код в живую попытку; если callback не проверен
на платформе, пользователь вставляет показанный Яндексом код в настройки.
При проблеме возврата кнопка кодового входа начинает новую попытку. Закрытие
настроек сохраняет попытку в памяти плагина; закрытие Obsidian требует нового входа.

Существующий пользователь может оставить ручной способ или выбрать вход через
Яндекс. Старый токен действует до сохранения кандидата. Плагин проверяет raw
удалённую папку новым токеном: путь и opaque resource ID должны совпасть с
сохранённым `remoteScope`. Другой аккаунт, удалённая/пересозданная папка или
неудачное чтение не заменяют старый токен и не создают новую папку. Старое состояние
без `remoteScope` сначала проходит обычную явную привязку на старом подключении.
При первой настройке без истории отсутствие папки допустимо: её создание остаётся
за обычным full. Переезд в другой аккаунт не является бесшовной сменой авторизации.

Во время попытки watcher продолжает наблюдать и сохранять локальные события, но
новые автоматические отправки, Force, backup и encryption actions недоступны.
Уже запущенная работа завершается на старом подключении. Кандидат ждёт окончания
сессий и native Disk writes, затем workflow занимает существующий configuration
reservation, проверяет root и сохраняет credentials общей snapshot queue.
Ожидание не занимает SyncCoordinator. После освобождения reservation запускается
обычный ручной full: merge, encryption admission и все защитные блоки сохраняются.

Отмена до принятия save сохраняет старый доступ. После начала принятого save
отмена недоступна: запись может уже состояться. Pause отзывает продолжение full до startup preflight, включая pause/resume во
время save; принятые credentials сохраняются. Resume во время browser attempt
не запускает старое подключение; mobile recovery сохраняет ожидающий hint до
отмены или окончания login. Unload запрещает публикацию в runtime;
последующие snapshots сохраняют последний подтверждённый auth tuple, чтобы старый
runtime не затёр его. Failed save не считается доказательством отсутствия записи:
сохраняется persistence block, нужен явный retry/repair.

Успешный login сначала сохраняет `manualSyncRequired=true`. Только успешный full
и его финальная запись снимают флаг. Ошибка сети, пароль, pause или failed final
save оставляют возможность обычного ручного «Синхронизировать», включая restart,
без обязательного повторного входа. UI также позволяет войти заново. Первый вход
не отменяет существующую явную паузу пользователя.

## Изоляция попыток и секретов

State и verifier — независимые случайные 32-byte значения, только в памяти.
Попытка живёт 10 минут; token POST имеет 30-секундный logical timeout без retry.
Отмена/timeout не отменяют уже отправленный native request: следующий token POST
ждёт его реального settlement. Поздний ответ не публикует credentials. Чужие state,
повторный callback и callback в другом vault не отменяют действующую попытку.
Идентификатор OAuth-устройства — стабильный SHA-256 от существующего device ID;
causal actor не пересоздаётся.

Плагин не журналирует код, verifier, OAuth URL, токены или raw provider errors;
ошибки представлены фиксированными категориями. Access token хранится открыто
только в локальном plugin data, как прежде. Кодовый input маскирован, не сохраняется
на диск. При этом сам Obsidian может журналировать protocol URL: гарантия плагина
не распространяется на host, browser или OS logs. Не пересылать их без проверки
и удаления чувствительных значений.

## Границы проверки

Автотесты исполняют настоящий controller, persistence, adoption workflow и full
с двумя независимыми локальными состояниями в plaintext/encrypted режимах;
подменены транспорт и внешние UI/lifecycle границы. Они проверяют результаты,
а не реальные браузер, Yandex consent, native Obsidian или мобильную маршрутизацию.
Ссылки на тесты и ручные случаи — `AUTH-001`–`AUTH-016` в каталоге сценариев.
Новый общий вход нельзя считать готовым к выпуску до реального PKCE-обмена и
ручной приёмки. Возврат к ручному токену остаётся доступен.
