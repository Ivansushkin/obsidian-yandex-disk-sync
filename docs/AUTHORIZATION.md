# Авторизация и переход с ручного токена

Новая установка выбирает «Вход через Яндекс». Существующие настройки с токеном
или Client ID распознаются как ручные: обновление не меняет подключение, baseline,
очереди, пароль, device ID или допуск к автоматической синхронизации. Выбор способа
в интерфейсе — локальный draft. Явное начало общего входа удаляет прежние ручные
Client ID и токен до открытия браузера; отмена их не восстанавливает.

## Включение общего приложения владельцем

В `src/auth/configuration.ts` настроен публичный Client ID, предоставленный
владельцем приложения. Автоматический возврат по callback URI включён для
тестирования на desktop, Android и iOS. Реальный PKCE-обмен и возврат в Obsidian
ещё требуют проверки на каждом устройстве.
При пустом Client ID интерфейс объясняет
недоступность общего входа и предлагает ручной способ. Нельзя использовать
идентификатор чужого приложения.

1. Зарегистрировать собственное приложение Яндекс ID **для авторизации
   пользователей**, с правами `cloud_api:disk.read` и `cloud_api:disk.write`.
   Не выбирать приложение только для собственных данных разработчика.
2. Проверить обмен `authorization_code` с PKCE S256 без Client Secret, включая
   повторное согласие и второй аккаунт. Настроить разрешённые redirect URI.
3. Проверить `obsidian://yandex-disk-sync-auth?vault=<URL-encoded vault name>`
   на каждой платформе, обработку query parameters и ограничения регистрации
   redirect URI у провайдера. Callback используется на всех платформах;
   перед выпуском каждая должна пройти реальный вход.
4. Перед сборкой задать `YANDEX_OAUTH_CLIENT_SECRET` в локальной `.env`.
   Для release CI задать `YANDEX_OAUTH_CLIENT_SECRET_2_2_0`: проверка
   опубликованного релиза повторяет сборку с этим же значением. Сборка
   включает секрет в `main.js`; значение не хранится в Git.
   Пройти `TC-AUTH-01` и обычный smoke двумя профилями на реальном Диске.

После входа refresh token сохраняется только в локальном plugin data. Перед
новой сетевой операцией OAuth-доступ обновляется, если до срока действия
осталось менее пяти минут. Это относится к холодному запуску, мобильному
восстановлению и планировщику. HTTP 401 в full/realtime/startup/mobile/scheduled
full вызывает отдельный refresh и не более одного нового запуска через обычную
очередь с новой startup invocation; уже отправленные записи не повторяются
непосредственно внутри transport. Backup и Force обновляют token перед
началом; после ошибки их явную операцию нужно повторить. Ответ refresh сохраняет access token,
новый refresh token и срок действия одним snapshot. Если Яндекс отказал в
refresh окончательно, требуется новый вход. При сетевой ошибке текущие
credentials и отложенная работа сохраняются. Через 30 секунд плагин повторяет
refresh и при успехе выполняет автоматический full до включения watcher и
scheduler. Если этот full временно не смог прочитать Диск, следующая попытка
назначается через 30 секунд. На скрытом мобильном приложении попытка ждёт
возвращения в видимое состояние. Пауза, выход, смена подключения, ручной режим
и выгрузка отменяют автоматическое продолжение; занятая очередь откладывает попытку.
Общий Client Secret в опубликованной сборке извлекаем и не служит защитой
токенов пользователя.

Источники протокола: [запрос кода и PKCE](https://www.yandex.ru/dev/id/doc/ru/codes/code-url),
[регистрация](https://yandex.ru/dev/id/doc/ru/register-client),
[тип приложения](https://yandex.ru/dev/id/doc/ru/register-auth),
[refresh](https://yandex.ru/dev/id/doc/ru/tokens/refresh-client).
Права, Redirect URI и работоспособность конкретного приложения ещё не подтверждены
ручной приёмкой.

## Пользовательский поток

На первой настройке пользователь выбирает отдельную удалённую папку, проверяет
фильтры и нажимает «Войти». Плагин открывает внешний браузер.
После согласия callback возвращает код в живую попытку. На Android/iOS возврат
из браузера открывает Obsidian и завершает вход. Пока попытка активна, страницу
входа можно открыть повторно или отменить вход в настройках. Если callback не
вернулся или попытка истекла, пользователь начинает новый вход. Закрытие настроек
сохраняет попытку в памяти плагина; закрытие Obsidian требует нового входа.

В обоих способах кнопка «Выйти» удаляет локальные Client ID, токен и метаданные grant
через общую snapshot queue и останавливает автоматизацию. Это локальный выход,
без отзыва разрешений приложения на стороне Яндекса. Путь, causal history, очереди,
pause и файлы сохраняются; пароль шифрования удаляется из `data.json` и работающий
codec сбрасывается. Перед выходом оба способа показывают одно подтверждение с
предупреждением об удалении локальных данных входа и пароля; отмена или закрытие
диалога оставляет подключение без изменений. Повторный вход проверяет прежний root
и запрашивает пароль для зашифрованного хранилища. Выход не обращается к Диску, ждёт текущие native writes и недоступен
во время активных операций. Ошибка save не публикует logout и блокирует автоматизацию;
после принятого save поздний snapshot старого runtime не восстанавливает credentials.
При незавершённом переходе шифрования или восстановлении Force выход отклоняется:
их checkpoint может содержать пароль, который нельзя удалить без потери возможности
восстановления. После завершения восстановления выход очищает все сохранённые
токены и пароли; salt, профиль шифрования, путь и история остаются для безопасного
повторного подключения. Начало общего входа с ручного подключения удаляет прежний
ручной токен и Client ID, сохраняя пароль до завершения перехода.
Пока токен отсутствует, статус предлагает вход или ручной токен, а Sync, Force, резервные
копии и действия с шифрованием в настройках недоступны. Параметры будущей
синхронизации и диагностика остаются доступными.

Ручное «Войти» проверяет root; оба входа ждут первого ручного Sync.

Существующий пользователь может оставить ручной способ или выбрать вход через
Яндекс. Перед новой попыткой прежние ручные credentials удаляются coherent save;
watcher продолжает наблюдать локальные изменения при заблокированных отправках.
Плагин проверяет raw
удалённую папку новым токеном: путь и opaque resource ID должны совпасть с
сохранённым `remoteScope`. Другой аккаунт, удалённая/пересозданная папка или
неудачное чтение не принимают кандидата и не создают новую папку. Старое состояние
без `remoteScope` сначала проходит обычную явную привязку на старом подключении.
При первой настройке без истории отсутствие папки допустимо: её создание остаётся
за обычным full. Переезд в другой аккаунт не является бесшовной сменой авторизации.

Во время попытки watcher продолжает наблюдать и сохранять локальные события, но
новые автоматические отправки, Force, backup и encryption actions недоступны.
Уже запущенная работа завершается на старом подключении. Кандидат ждёт окончания
сессий и native Disk writes, затем workflow занимает существующий configuration
reservation, проверяет root и сохраняет credentials общей snapshot queue.

Отмена до принятия grant save не восстанавливает удалённый ручной доступ. После начала принятого save
отмена недоступна: запись может уже состояться. Принятые credentials сохраняются.
Resume во время browser attempt
не запускает старое подключение; mobile recovery сохраняет ожидающий hint до
отмены или окончания login. Unload запрещает публикацию в runtime;
последующие snapshots сохраняют последний подтверждённый auth tuple, чтобы старый
runtime не затёр его. Failed save не считается доказательством отсутствия записи:
сохраняется persistence block, нужен явный retry/repair.

В OAuth-режиме поле ручного `settings.clientId` очищается и при загрузке существующего
состояния с первой coherent записью до автоматизации. Действующий access token
остаётся в единственном `yandexTokenSecret`; Client ID общего приложения остаётся
в конфигурации/grant. Ручные инпуты не отображают OAuth token. Ввод собственного
Client ID или токена атомарно переводит подключение в manual и удаляет прежний OAuth
grant/token, сохраняя только явно введённые ручные данные.

## Изоляция попыток и секретов

State и verifier — независимые случайные 32-byte значения, только в памяти.
Попытка живёт 10 минут; token POST имеет 30-секундный logical timeout без retry.
Отмена/timeout не отменяют уже отправленный native request: следующий token POST
ждёт его реального settlement. Поздний ответ не публикует credentials. Чужие state,
повторный callback и callback в другом vault не отменяют действующую попытку.
Идентификатор OAuth-устройства — стабильный SHA-256 от существующего device ID;
causal actor не пересоздаётся.

Плагин не журналирует код, verifier, OAuth URL, токены или raw provider errors;
ошибки представлены фиксированными категориями. Access token хранится открыто
только в локальном plugin data, как прежде. Код callback не сохраняется на диск.
При этом сам Obsidian может журналировать protocol URL: гарантия плагина
не распространяется на host, browser или OS logs. Не пересылать их без проверки
и удаления чувствительных значений.

## Границы проверки

Автотесты исполняют настоящий controller, persistence, adoption workflow и full
с двумя независимыми локальными состояниями в plaintext/encrypted режимах;
подменены транспорт и внешние UI/lifecycle границы. Они проверяют результаты,
а не реальные браузер, Yandex consent, native Obsidian или мобильную маршрутизацию.
Ссылки на тесты и ручные случаи — `AUTH-001`–`AUTH-020` в каталоге сценариев.
Новый общий вход нельзя считать готовым к выпуску до реального PKCE-обмена и
ручной приёмки. Возврат к ручному токену остаётся доступен.
