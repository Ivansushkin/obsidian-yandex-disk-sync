# Проверка оптимизаций полного синка

## Выборка метаданных

Только обычный full запрашивает поля, нужные для обхода и physical fingerprints.
Force, backup и переходы шифрования используют полный ответ API. У файла обязателен
целый неотрицательный `size`. Неполная projected page перечитывается без `fields`;
повторно неполная страница завершает full ошибкой, без принятия удалений или
продвижения baseline. После неполной страницы или ответа 400/406 проекция
отключается для всех следующих запросов этого обхода, включая другие папки.
Уже отправленные параллельные запросы завершаются штатно. Следующий full может
снова попробовать проекцию.

Реальный выпускной замер проводится на двух независимых профилях Obsidian и
отдельном тестовом хранилище Яндекс Диска, затем на мобильном Obsidian. Для
небольшого хранилища, большого плоского хранилища и дерева с множеством папок
сделать не менее десяти тихих полных проходов до и после изменения. Сопоставить
медиану и p95 общего времени, время remote scan, количество запросов и объём
JSON-ответов. Отдельно проверить холодный проход, изменённый файл, пагинацию,
шифрование и прерывание соединения. Измерять одинаковое состояние и сеть;
выводить только длительности, счётчики и размеры, без токенов, путей, содержимого
файлов и canonical index. Синтетический `check:sync-efficiency` не заменяет этот
замер.

`npm run probe:resource-fields` делает пять пар read-only GET для первой страницы
`YANDEX_DISK_PROBE_PATH` (по умолчанию `disk:/`) с текущим
`YANDEX_DISK_TOKEN`. Он не выводит путь, токен или тело ответа, только размеры и
длительности. Это быстрый smoke совместимости и передачи метаданных, но не
оценка полного синка и не доказательство равенства всей пагинации.

Если projected ответ расходится с полным по path/type/modified/size/hash или
заметно увеличивает число запросов из-за fallback, проекцию не выпускать до
исправления. Положительный эффект оценивать по общему времени full: экономия
байтов без сокращения времени не считается ускорением синхронизации.

## Эксперимент с ревизией Диска

`npm run probe:disk-revision` отправляет только read-only запрос
`GET /v1/disk?fields=revision`. Он читает `YANDEX_DISK_TOKEN` из окружения,
не принимает токен аргументом и не выводит заголовки или тело ответа. Токен
настраивается вне чата и командной истории. Скрипт печатает HTTP-статус, время,
тип и число ревизии, если оно является безопасным неотрицательным целым.

На отдельном тестовом аккаунте выполнить пробу с действующим токеном текущего
приложения до и после создания, перезаписи, удаления и перемещения файла из
первого и второго профиля. Повторить в шифрованном режиме и при посторонних
изменениях вне папки синхронизации. Сравнить каждый результат с обычным full.
Неизменившаяся ревизия при реально изменившемся ресурсе — запрет на fast path.
Ошибка, отсутствие поля, недоступность с текущими правами или неустойчивая
семантика также оставляют плановые полные проходы без изменений. Никаких новых
OAuth-разрешений этот эксперимент не запрашивает.

Даже при успешном опыте нужен отдельный релизный gate: тихий сценарий с
интервалом 5 минут должен экономить не менее 20% wall time и 25% запросов;
активный сценарий не должен заметно ухудшать p95 и добавлять более 5% запросов.
Восстановление после сна, ручной/стартовый синк и выключенный watcher никогда
не используют fast path. До подтверждения этого gate в продукте нет пропуска
полного синка по ревизии.
