# Пользовательские сценарии синхронизации

Этот документ — нормативный каталог поведения синхронизации. Изменение
алгоритма требует актуализации затронутых сценариев и подходящей автоматической
или ручной проверки. Создавать юнит для каждой строки каталога запрещено.

По [политике тестирования](../AGENTS.md#documentation-and-testing) юниты
допустимы только в компактном виде для сложных алгоритмов и связок функций.
Один тест может подтверждать несколько сценариев, если действительно проверяет
их результаты. При объединении тестов обновляйте ссылки; при удалении указывайте
существующий ручной case либо `manual-required`. Эти ссылки описывают способ
проверки, а не подтверждают состоявшийся успешный прогон.

## Как читать каталог

- `P0` — возможна незаметная потеря или раскрытие данных.
- `P1` — синхронизация может остановиться, повторять операцию или потребовать
  ручного восстановления.
- `P2` — проблема производительности, диагностики или удобства.
- `auto: \`точное имя теста\`` — сценарий проверяется указанным исполняемым
  тестом; все перечисленные тесты должны пройти в release workflow.
- Generic suite labels (`fault`, `integration`, `fake-yandex` и подобные) не
  являются release evidence.
- `manual-required` — требуется отдельная проверка на реальном Яндекс Диске и
  Obsidian; `manual: \`TC-xx\`` ссылается на конкретный smoke case.
- Под `canonical` понимается `.obsidian-sync-index.json`.
- `Physical` — фактические пользовательские файлы на Яндекс Диске.
- Новое устройство сначала получает существующий canonical: облачные версии
  заменяют локальные с protective copies. После этого файл без baseline считается
  новым пользовательским состоянием; неизвестные local-only файлы сохраняются.
- Пустые папки отдельно не синхронизируются.

Для каждого сценария применяются варианты из [матрицы](#матрица-вариантов),
если строка явно не ограничивает режим или число устройств.

[архитектуре](ARCHITECTURE.md). Чистый reducer не подтверждает physical writes;
commit proof не заменяет свежие authority/codec guards. Алгоритмические tests
проверяют свои boundaries, реальные Obsidian/Yandex исходы требуют manual evidence.

### Watcher queue и submitted identity

Для MOVE-017/018/024/025/026/027/029/035…041, SYNC-024/031 и INV-008
queue reduction сохраняет ID/seq/epoch, submitted predecessor, distinct successor
и upload handoff. Parent notification не переписывает submitted child; parent
остаётся следующей durable операцией. Canonical/physical writes эта pure boundary
не выполняет.

Проверки: `queue absorption follows rename targets without swallowing unrelated source work`,
`queue absorption follows rename targets without swallowing unrelated source work`,
`upload receipts release pending rename predecessors and advance accepted edit baselines`,
`upload receipts release pending rename predecessors and advance accepted edit baselines`,
`file and folder chains retain running identities across JSON restart`,
`folder notifications preserve submitted child rename snapshots`.
Receipt-before-ACK, offline return и два независимых состояния проверяют flow
cases таблиц; реальные Obsidian notifications остаются manual-required.

### Watcher durability и lifecycle barriers

PERF-013 проверяет arrivals до/во время отложенного save, общий отказ нескольких
waiters и remote admission, отсутствие скрытого success без новых events,
успешный repair и JSON restart. Arrival между завершением callback и release
runner также попадает в durable queue, без зависания следующего wait.
На отказе canonical/physical остаются прежними,
последний успешно сохранённый snapshot содержит исходные IDs/queues; в памяти
сохраняется более поздняя очередь. После repair последний snapshot переживает
restart, два независимых local states получают точные bytes, pending watcher,
mutation и physical-action queues пусты. Новый test выполняет реальные sync
алгоритмы с synthetic transport; он не проверяет platform notification timing.

SYNC-023/024/026 и MOVE-038/039/040 сохраняют прежние outcomes при новом scheduling.
Full cutoff и late-event replay проверяют
`full barrier settles captured uploads only after success and retains later work`,
`session resume replays only new paused events after success` и plaintext/encrypted
`full waits for the rename batch and retains edits made while it runs`.
`session resume replays only new paused events after success` оставляет captured queue без ACK;
`full barrier acknowledgement is persisted before resume completes` проверяет
также stopped watcher. `post-full rename acknowledgement persists before observed revision advances`
проверяет pre-observed settlement; обычный captured-upload ACK сохраняется
в resume до освобождения coordinator. Тот же PERF-013 test проверяет stopped settlement с прежним Force cutoff:
новый same-path event сохраняет ID/bytes, remote work не запускается. Полный
Force протокол (без проверки всех late-event interleavings) покрывают `Force plaintext without archive replaces collisions while paused and gates offline return`
и `Force encrypted without archive replaces collisions while paused and gates offline return`.
Initial receive, foreign epoch и restart дополнительно покрывают существующие
sync-user-flows/rename-batch outcomes; реальные два Obsidian-профиля/Yandex
и notification order остаются manual-required по исходным cases.

### Актуальные callbacks

INIT-028 и FORCE-DIRECT-012 требуют epoch-bound accept/preserve/later. Замена callback
во время canonical load должна быть видна текущей сессии; failed adoption сохраняет
baseline/queues, успешное схождение — exact bytes и пустые очереди обоих устройств.
Проверки: `plaintext real Force replacement and foreign adoption preserve offline edits`,
`encrypted real Force replacement and foreign adoption preserve offline edits`,
`an explicit epoch choice accepts replacement without Force ping-pong`.
Module/stage map — в [архитектуре](ARCHITECTURE.md); live UI — manual-required.

## Матрица вариантов

Каждый новый алгоритм проверяется минимум pairwise-набором по следующим осям.
Для `P0`-сценариев обязательны все применимые сочетания режима и порядка
операций при функциональной приёмке. Матрица не требует отдельного юнита на
каждое сочетание: алгоритмические проверки выбираются по различающимся рискам,
остальные варианты проверяются подходящим ручным прогоном.

| ---------- | ------------------------------------------------------------------------------ |
| Устройства | 1, 2 одновременно online, 2 с одним offline, 3 с разным порядком               |

## Правило выпуска

Для каждого `P0` и `P1` указывается существующая автоматическая проверка либо
ручной способ проверки. Release требует датированных результатов реального
прогона двух независимых профилей Obsidian против Яндекс Диска; записи в
release evidence должны соответствовать проверенной ревизии. `manual-required`
и ссылка на smoke-case сами по себе не означают успешного прогона.

Новую ошибку фиксируют в соответствующем сценарии и воспроизводят существующим
тестом либо вручную. После исправления повторяют подходящую проверку. Новый
юнит допустим только по критериям AGENTS.md и не является обязательным условием
исправления.

## Lookup, ancestry и физические guards

PERF-001/002/003/004/010: merge индексирует latest put baseline один раз, baseline
и full-upload проходы — latest matching (path, SHA), pruning — ancestors живых
files. Folder merge/replay использует snapshot membership с актуальной causal
metadata на каждом шаге. Canonical/local/physical исходы, порядок FIFO и IDs/epoch
сохраняются; repeated uploads одного path/SHA не выделяют новый sequence.
Auto: `full upload planning preserves latest matching FIFO identities across repeated paths`;
`folder tombstone lookup selects the newest ancestor in path-depth work`;
`folder delete planning skips history, siblings and folder roots at any depth`;
`canonical file mutations enforce deletion, causality and FIFO before stamping a merge`;
`folder deletion preserves foreign and unknown children but recognizes its own FIFO predecessor`.
PERF-013 watcher save/settlement и существующий bounded rename contract не меняются.
Bounded development probe N/2N сравнивает реальные baseline/current алгоритмы и
считает visits/copies, без latency thresholds; данные и границы — в [отчёте](REFACTOR_REPORT.md#что-измерено).
Измерение end-to-end latency и mobile memory остаётся manual-required.

FDEL-004/005/006/007/009/016/017/018: ancestry membership не кеширует metadata.
Новый или конкурентный child остаётся live; same-device predecessor удаляется
только с прежним sequence proof. Overlapping tombstones исполняются последовательно.
Папка с новым physical/excluded child не удаляется и не порождает новый canonical
exact delete. Auto: `canonical file mutations enforce deletion, causality and FIFO before stamping a merge`;
`folder tombstones delete only unchanged known descendants`;
`folder deletion preserves foreign and unknown children but recognizes its own FIFO predecessor`;
`optional remote pruning retains an empty directory and a late protected descendant`.

DEL-017/SAFE-018: предварительный Set ancestors не является authority. На каждой
DELETE/retry свежие canonical/emptiness и существующие physical fingerprint checks
могут отменить действие. Restored physical bytes сохраняются, obsolete action
снимается, непроверенный DELETE не подтверждает local baseline/canonical успех.
Auto: `physical delete retry preserves a foreign restored file`;
`DELETE guard failures are not treated as resource absence`;
`DELETE retry revalidates revoked authority before sending another request`.

PATH-001/003/005/006: полный preflight и final local scan после asynchronous
preparation сохранены. NFC/case/file-directory/ancestor collisions блокируют write;
байты local/physical и canonical не подтверждаются ложным download. Protected и
raw encrypted paths используют общую path-utils policy. Auto:
`portable path collisions block Force remote before local writes`;
`guarded local creation preserves a file created while parents are prepared`;
`guarded local update does not recreate a file deleted during identity verification`;
`path filtering protects plugin storage while allowing other configured plugins`.
Реальные платформенные Unicode/case и два Obsidian-профиля/Yandex остаются
manual-required; адресный final probe без доказанной эквивалентности не добавлен.

Historical server-fencing diagnostic (outside the direct Force guarantee): `npm run test:force-fencing` executes
`tests/release-gates/force-fencing.test.ts` with preservation expectations.
It is separate from the ordinary regression suite and currently fails; this is
not passing evidence and is not a release gate for direct Force.
See [FORCE_SYNC.md](FORCE_SYNC.md) for the current contract and real-profile checks; FORCE_SAFETY_VALIDATION.md contains historical fencing evidence.
