# Rename/edit and receiving-device latency

Approved plan: the implementation request in this chat (2026-10-23).

## Contract

Optimize ordinary startup/full/realtime without changing persisted schemas,
causal FIFO, encryption profiles, mandatory protection, Force semantics or
coordinator ownership. Read observations never authorize writes. New fast paths
must fail closed and preserve JSON restart, late events and failed persistence.

## Tasks

1. Capture the existing efficiency baseline and extend real algorithm probes for
   rename/edit, duplicate notification, late successor and receiving-device restart.
2. Apply published local tombstones without a canonical transaction; distinguish
   observed intent from a commit proof and retain final read-only validation.
3. Confirm unchanged realtime events before sequence allocation, with a distinct
   ephemeral receipt and fresh logical/physical/encryption validation.
4. Remove duplicate move cleanup validation, reuse only hash-pinned verified target
   evidence, overlap independent reads and avoid canonical MOVE parent preparation.
5. Combine healthy startup service reads, overlap full scans and defer old-backup
   sweeping through the existing coordinator after successful startup.
6. Add safe build/stage diagnostics, update normative scenarios and documentation,
   run the complete verification and review the final working diff.

## Verification

Reuse existing two-device functional fixtures in plaintext/encrypted modes and
existing restart/failure scenarios. Assert bytes, baselines, queues, IDs/FIFO and
absence of false acknowledgement, not only request counts. Demonstrate overlap
with gates; compare complete transport counters, not wall time alone.

Run lint:fix, format, test, lint, build, format:check and git diff --check.
Build output must be suppressed before capture because the trusted build script
loads local configuration and may print its destination. Never inspect .env.
Real two-profile Obsidian/Yandex/mobile smoke remains a separate manual gate.

## Measured result

The same extended runner was executed against exported committed baseline 6685adf
and the final working sources. Counts below include metadata/link API requests,
direct body transfers and MOVE/DELETE requests. These are controlled functional
fixtures with synthetic network delay, not real-device latency measurements.

| History                                  | Plain HTTP requests before → after | Encrypted HTTP requests before → after |
| ---------------------------------------- | ---------------------------------- | -------------------------------------- |
| Rename/edit, then duplicate notification | 125 → 89                           | 131 → 95                               |
| Rename/edit, then actual late edit       | 125 → 109                          | 131 → 115                              |
| Rename after source PUT started          | 105 → 99                           | 111 → 105                              |
| Receiving device JSON restart            | 54 → 37                            | 55 → 39                                |
| Following full with no changes           | 12 → 12                            | 15 → 15                                |

The duplicate history uses two canonical transactions instead of three and one
user PUT instead of two. A real late edit still uses its own PUT and transaction.
The receiving history downloads the target and deletes the old local file without
canonical MOVE/PUT; canonical bytes remain unchanged. Its next full reports 0/0/0
with empty queues. Byte, canonical, baseline and durable receipt oracles pass in
both modes.

Full local/remote scan overlap and encrypted startup raw-body overlap are verified
with explicit gates. Encrypted startup discovery can add one metadata GET while
overlapping independent service downloads; plaintext startup retains its previous
path. Bulk directory metadata counts vary with scheduling: the final plain 42-file
upload used 495 API reads and a repeat used 492, compared with baseline 494. No
blanket reduction or real-world seconds claim is made for those paths.

Its replay chain lasts 59.874 s (11:03:01.944–11:04:01.818 UTC); the earlier log
lasts 49.049 s (08:09:22.369–08:10:11.418 UTC). Three canonical transactions remain:
11.409 + 11.469 + 10.292 = 33.170 s, compared with 26.395 s earlier. Startup through
watcher readiness is 13.120 s, compared with 13.647 s earlier. These are single

The histories differ: the new rename selects `remote-move`, proving its captured
target SHA matched the canonical source; the old rename materializes changed
content. The new rename still has a subsequent upload event with a 27-byte
snapshot. The existing log cannot distinguish changed local content from a
conservative fallback caused by another eligibility check. It is insufficient to
attribute the extra transaction to a redundant notification or to a real late edit.
No new receiving-device log was supplied, so the mobile fast path remains unverified
in this runtime follow-up.

The local scan takes 33 ms and overlaps the 3.905 s remote scan. Their overlap is
working, but it cannot materially reduce this vault's observed delay. No queue
waiting or retry is reported in the supplied replay. Most visible time remains in
canonical transactions and the reads/guards around them.

Follow-up changes are diagnostic only: each canonical attempt reports aggregate
stage milliseconds and transport deltas, including error/retry paths. Realtime
preparation reports aggregated unchanged-check decisions, and rename planning
records snapshot size and whether its SHA matches the source. No payloads, URLs,
credentials or extra network operations are introduced; write and ACK order remain
unchanged. A new log after reloading this build is needed before selecting another
safe reduction in the canonical critical path.
